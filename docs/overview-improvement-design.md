# Overview 改善設計書

## 1. 目的

1つのプロジェクトを cc-sdd で開発する際に、チームリーダーが開発状況を把握し、作業の調整や支援を判断できる Overview を提供する。

Overview を開くことで、次の問いに答えられるようにする。

- 現在、どの Spec がどの工程にあるか
- どの仕事が止まり、何を待っているか
- 次に着手できる仕事は何か
- 前回確認したときから何が変わったか
- 何が完了し、何が残っているか

工程の承認は各担当者のワークフローとして扱う。承認待ちは状態として表示するが、チームリーダーへの対応依頼とはみなさない。

## 2. 対象範囲

既存の Overview を改善する。Specs、Tasks、Runs、Sessions の既存機能を活用し、詳細画面へ移動する入口を提供する。

対象とする情報は次のとおり。

- プロジェクト内の Spec
- Spec の現在の工程
- タスクの完了数と総数
- 実行中・入力待ち・失敗などの実行状態
- 明示的に記録されたブロックや依存関係
- 確認可能な検証結果
- 記録から確認できる最近の変化

担当者管理、納期管理、チーム共有バックエンドの新設は本設計の対象外とする。既存機能に情報がある場合のみ表示に利用する。

## 3. 設計方針

### 3.1 進行中の仕事を中心にする

進行中の Spec と、その現在地を画面の中心に置く。

完了済み Spec が増えても、進行中の仕事が埋もれない構成にする。

### 3.2 工程・進捗・実行状態を分ける

次の情報を別々に表示する。

| 情報 | 例 |
|---|---|
| 工程 | 要件、設計、タスク分解、実装、検証 |
| タスク進捗 | 4/8 |
| 実行状態 | 実行中、入力待ち、未実行、失敗 |
| 停止理由 | 依存 Spec の契約確定待ち、未決事項あり |

「実装工程にある」と「エージェントが実行中である」を混同しない。

### 3.3 確認できる事実を表示する

実行記録がない場合、稼働中・停止中を推測しない。

更新が古いという理由だけで「停滞」「ブロック」と判定しない。

情報が取得できない場合は、空欄や正常扱いにせず「未確認」「情報なし」と表示する。

### 3.4 詳細情報への入口にする

Overview は状況把握に必要な情報に絞る。ログ全文、全タスク、全セッション履歴は既存の詳細画面で確認する。

## 4. 画面構成

上から次の順に配置する。

1. ヘッダー・集計範囲
2. プロジェクト概況
3. 進行中の Spec
4. 依存関係・着手候補
5. 最近の変化
6. 完了済み Spec

狭い画面では各セクションを縦に並べる。

## 5. 各セクションの仕様

### 5.1 ヘッダー・集計範囲

表示項目：

- プロジェクト名
- 最終取得時刻
- 更新ボタン
- 情報の集計範囲

集計範囲は、実際に取得できる範囲を明示する。

例：

> Spec：このワークスペース  
> 実行状態：この VS Code ウィンドウで取得できた記録

ローカルで取得した情報を、チーム全体の稼働状況として表示しない。

### 5.2 プロジェクト概況

次の件数をコンパクトに表示する。

| 項目 | 意味 |
|---|---|
| 進行中 | 完了扱いになっていない開発中の Spec |
| ブロックあり | 明示的な停止理由を持つ Spec |
| 検証待ち | 実装タスクが完了し、必要な検証の完了を確認できていない Spec |
| 完了 | プロジェクトで定めた完了条件を満たす Spec |

各件数をクリックすると、該当する Spec に一覧を絞り込む。

件数は相互排他的とは限らない。例えば「進行中」に「ブロックあり」が含まれる場合は、ラベルや補足で関係を明確にする。

全タスクの合計進捗は補助情報として表示できるが、プロジェクト全体の完成率には換算しない。

### 5.3 進行中の Spec

画面の主要セクション。Spec を横断して比較できる一覧とする。

#### 表示項目

| 項目 | 内容 |
|---|---|
| Spec | 表示名と識別子 |
| 工程 | 現在の開発工程 |
| タスク | 完了数 / 総数 |
| 現在の状況 | 実行中タスク、承認待ち、入力待ちなど |
| 停止理由 | 明示的なブロックがある場合に表示 |
| 更新 | Spec の最終更新時刻 |
| 操作 | Spec 詳細や該当 Run への移動 |

表示例：

| Spec | 工程 | タスク | 現在の状況 |
|---|---|---|---|
| 認証機能 | 設計 | — | 設計レビュー待ち |
| 通知機能 | 実装 | 4/8 | タスク5を実行中 |
| 履歴機能 | 実装 | 0/6 | 認証機能の契約確定待ち |
| README | 検証 | 2/2 | 検証結果未確認 |

#### 並び順

初期表示では次の順とする。

1. 明示的なブロック・失敗がある Spec
2. 実行中の Spec
3. 入力待ち・レビュー待ちの Spec
4. その他の未完了 Spec

同じ区分内では、直近の活動が新しい順に並べる。

自動更新で頻繁に行が移動しないようにし、選択中の行とスクロール位置を維持する。

#### 狭い画面での表示

表が収まらない場合は、同じ情報を縦型の行にする。

```text
通知機能                          実装
4/8 タスク完了
タスク5を実行中
更新：10分前              ［実行を見る］
```

重要な状態や停止理由を省略しない。

### 5.4 依存関係・着手候補

明示的に記録された依存関係を基に、作業順序を判断する情報を表示する。

表示対象：

- 他の Spec を待っている仕事
- 後続の Spec に影響する未完了の依存
- 依存条件が満たされ、次工程への着手条件を満たす Spec
- 上流変更により再検証が必要と記録された Spec

初期実装では一覧形式とする。依存関係のグラフ表示は必須としない。

表示例：

```text
履歴機能 → 認証機能の契約確定待ち
通知機能 → 着手条件を満たしています
検索機能 → 共通スキーマ変更による再検証待ち
```

依存情報が存在しない場合は「依存情報なし」と表示する。「依存なし」「着手可能」とは判定しない。

### 5.5 最近の変化

記録されたイベントを新しい順に表示する。

対象イベント：

- Spec の追加
- 工程の変更
- タスクの完了
- 実行の開始・終了・失敗
- ブロックの発生・解消
- 検証結果の記録
- 再検証が必要になったことの記録

各イベントには次を表示する。

- 対象 Spec
- 変化の内容
- 発生時刻
- 関連する詳細へのリンク

初期表示は直近10件とし、必要に応じて追加表示する。

「前回確認から」の表示を実装する場合は、閲覧時点を明示的に保存する。初回表示時や履歴を取得できない場合に、過去の出来事を推測で生成しない。

履歴基盤がない場合は、当面「最近更新された Spec」を表示する。この場合、更新時刻だけから変更内容を生成しない。

### 5.6 完了済み Spec

初期状態では折りたたむ。見出しに件数を表示する。

展開時には次を表示する。

- Spec 名
- 完了状態
- 検証結果の有無
- 完了時刻。記録がなければ最終更新時刻
- 詳細へのリンク

既存の `done` がタスク完了だけを意味する場合は、その状態を検証済みと読み替えない。

## 6. 状態の扱い

### 6.1 実装完了と検証完了

次を区別する。

| 状態 | 判定根拠 |
|---|---|
| 実装中 | 未完了の実装タスクがある |
| 実装完了 | 対象の実装タスクがすべて完了 |
| 検証待ち | 必要な検証が未実施、または結果未確認 |
| 検証失敗 | 有効な検証記録に失敗がある |
| 検証済み | 対象に対する必要な検証の成功を確認できる |

検証済みの判定には、検証結果が現在の成果物に対応していることが必要。対応関係を確認できない場合は「検証結果あり・現在の状態への適用は未確認」とする。

### 6.2 承認待ち

承認待ちは対象 Spec の状態として表示する。

承認者が記録されていない場合は、チームリーダーを承認者として割り当てない。Overview 全体を承認依頼の受信箱として扱わない。

### 6.3 実行失敗とブロック

実行失敗は、その実行でエラーが発生したことを示す。

Spec 全体のブロックは、先に進めない理由が明示されていることを示す。

過去に失敗した Run があるだけで、現在の Spec をブロック扱いにしない。

### 6.4 複数の実行

同じ Spec に複数の有効な実行がある場合、1件に上書きせず「2件実行中」などと表示し、一覧を確認できるようにする。

## 7. データ取得・実装方針

実装前に既存の状態モデルと表示ロジックを確認し、Overview 独自の工程判定を重複して作らない。

表示用のデータには、少なくとも次の情報を持たせる。

- Spec 識別子・表示名
- 工程
- タスク完了数・総数
- 実行状態と関連 Run
- ブロック理由
- 依存関係
- 検証状態と根拠
- 更新時刻
- 各情報の取得元・取得範囲

情報が存在しない場合と、取得に失敗した場合を区別する。

更新は既存のファイル監視・実行通知を利用する。画面更新時に、フィルター、折りたたみ状態、選択、スクロール位置を維持する。

## 8. 実装順序

### 第1段階：既存情報で現在地を分かりやすくする

- 集計範囲を表示する
- 概況の集計を整理する
- 進行中の Spec を一覧化する
- 工程と実行状態を分離する
- 完了済み Spec を折りたたむ
- 既存の Spec・Run 詳細へ移動できるようにする

### 第2段階：停止理由と検証状況を表示する

- 明示的なブロック理由を表示する
- 実装完了と検証済みを区別する
- 情報なし・未確認・取得失敗を表示する

### 第3段階：依存と変化を把握できるようにする

- 記録済みの依存関係を表示する
- 着手条件を判定できる場合に着手候補を表示する
- 最近の変化を表示する
- 履歴基盤がある場合に前回確認からの差分を表示する

## 9. 受け入れ条件

- Overview から、進行中の各 Spec の工程と現在の状況が分かる
- 工程が実装でも、実行中でなければ実行中と表示されない
- 承認待ちがチームリーダーへの対応依頼として表示されない
- 明示的なブロックには理由が表示される
- 更新が古いだけの Spec をブロックと判定しない
- タスク完了数だけで検証済みと判定しない
- 情報がない状態を、問題なしと誤認させない
- ローカルの実行情報をチーム全体の状態として表示しない
- Spec と Run の詳細へ移動できる
- 完了済み Spec が増えても進行中の仕事を確認しやすい
- 自動更新で閲覧位置や選択が失われない
- 狭いエディター領域でも、現在の状況と停止理由を確認できる
