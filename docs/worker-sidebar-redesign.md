# 個人作業用サイドバー再設計案

## 1. 目的

左サイドバーの Specs / Tasks / Sessions を、個人作業者が対象を選び、工程を実行し、中断後に再開し、検証まで完了できる作業場所として再設計する。

Overview はプロジェクト全体の把握と調整、左サイドバーは個々の作業の実施を担う。

本書は実装前の設計要件である。既存機能の有無は実装時に確認し、既存の状態モデル・実行機構・セッション管理を活用する。

## 2. 最重要の完了条件

**実装が終わっただけでは Spec を完了にしない。必要な検証を実施し、その成功を現在の成果物に対して確認できた時点で完了とする。**

以下はそれぞれ別の事実として管理する。

- 実装タスクがすべて完了していること
- エージェントの実行が終了したこと
- 検証を実施していること
- 必要な検証が成功していること
- Spec の完了条件を満たしていること

タスクのチェック数や Run / Session の正常終了だけを根拠に、Spec に完了マークを付けない。

## 3. 共通の作業フロー

```text
Spec を選ぶ
  → 要件 → 設計 → タスク分解 → 実装
  → 検証
      → 成功・完了条件を満たす → 完了
      → 失敗 → 修正 → 再検証
      → 未実施・結果不明 → 検証待ちのまま
```

工程ごとの確認・承認が必要な場合は、既存の cc-sdd ワークフローに従う。承認者をチームリーダーと決めつけない。

「検証」は画面上で独立した工程として見せる。独立した新規コマンドの存在を前提とせず、実際の検証手段と既存の実行機構へ接続する。

## 4. 3つのビューの役割

| ビュー | 役割 |
|---|---|
| Specs | 作業対象を選び、工程・現在の状態・次の操作を確認する |
| Tasks | 選択中 Spec の実行単位を選び、実装と検証の残作業を確認する |
| Sessions | 選択中 Spec の実行状況を確認し、会話や作業を再開する |

Specs 内に詳細タスクを重複表示することは避け、工程から Tasks の対応箇所へ移動できるようにする。

## 5. Specs の設計

### 5.1 工程表示

各 Spec の配下に、次の工程を表示する。

1. 要件
2. 設計
3. タスク分解
4. 実装
5. 検証

現在の工程を強調し、完了した工程は控えめに表示する。工程と実行状態は分離する。

表示例：

```text
通知機能 · 検証待ち
  ✓ 要件
  ✓ 設計
  ✓ タスク分解
  ✓ 実装 8/8
  ○ 検証 未実施
  次：検証を開始
```

検証成功後：

```text
通知機能 · 完了
  ✓ 要件
  ✓ 設計
  ✓ タスク分解
  ✓ 実装 8/8
  ✓ 検証 成功
```

### 5.2 次の操作

対象と実行内容が分かる具体的な操作名を表示する。

| 状況 | 次の操作例 |
|---|---|
| 要件未作成 | 要件を作成 |
| 設計確認待ち | 設計を開く |
| 実装可能・未実行 | 実装を開始 |
| 実装中 | 実行を開く |
| 実装タスク完了・検証未実施 | 検証を開始 |
| 検証失敗 | 検証結果を開く |
| 修正後・以前の検証結果が無効 | 再検証を開始 |
| 完了 | 検証結果を確認 |

開始操作の前には、対象 Spec・工程・実行範囲を確認できる表示を用意する。毎回の追加確認ダイアログは必須にしない。

### 5.3 状態表現

「実装工程」と「実行中」を混同しないよう、例えば「実装・未実行」「実装・実行中」「検証・入力待ち」と表示する。

Spec の完了を示すアイコン・ラベルは、検証まで完了した場合に限って使用する。

## 6. Tasks の設計

### 6.1 選択中 Spec への連動

Specs で選んだ対象のタスクを表示し、ビュー上部に対象 Spec 名を常に表示する。

親タスクを展開したとき、実際に実行する子タスクと、その状態が分かるようにする。

### 6.2 実装と検証の表示

実装タスクの進捗と、Spec 全体の完了条件を分けて表示する。

```text
通知機能

実装 8/8
  ［完了タスクを表示］

検証
  ○ 必要な検証が未実施
  ［検証を開始］
```

検証項目が定義されている場合は、その一覧と結果を表示する。例えば要件との整合性確認、テスト、ビルド、型チェック、実機確認など、対象 Spec に必要な項目を利用する。

すべての Spec に同じ検証項目を固定で要求しない。文書変更などにも適切な検証方法を定義する。検証項目が未定義なら「検証条件未定義」と表示し、定義するための導線を提供する。

既存の tasks.md に検証タスクが含まれる場合は、そのタスクと検証結果を対応付ける。同一の作業を別タスクとして二重生成しない。ただし、検証タスクへのチェックだけで検証成功を確定しない。

### 6.3 タスク状態と操作

| 状態 | 表示する情報 |
|---|---|
| 次の候補 | 未完了で、確認できる着手条件を満たすタスク |
| 実行中 | 対応する有効な Run と実行対象 |
| 待ち | 明示された依存・判断待ちの理由 |
| 完了 | 完了したタスク。折りたたみ可能 |

提供する操作：

- tasks.md の該当位置を開く
- 対応する Run を開く
- このタスクを実行する
- ここから残りを実行する
- 検証結果を開く
- 実行中タスクへ移動する

実行範囲の指定は、実際の実行機構が対応する範囲で提供する。実行中の対象への重複開始を防ぎ、有効な Run があれば開けるようにする。

実行中タスクは強調するが、自動更新で選択・展開状態・スクロール位置を移動させない。

## 7. Sessions の設計

### 7.1 表示範囲

初期表示は選択中 Spec に絞る。「すべての Spec」へ切り替え可能にする。

選択中 Spec に属する実行中・入力待ちのセッションを上部に表示し、終了したセッションの履歴と分ける。全 Spec に実行中のセッションがある場合は、件数と全体表示への導線を用意する。

### 7.2 表示項目

- Spec 名。対象が不明ならその旨
- 工程。検証セッションも識別可能にする
- 実行状態
- 記録から取得できる最後の活動内容
- 開始時刻・最終活動時刻
- 再開または関連 Run を開く操作

トークン数は補助情報として扱う。

```text
通知機能の Sessions

● 検証 · 実行中
  統合テストを実行中
  ［実行を開く］

○ 実装 · 終了
  実装タスク 8/8。Spec は検証待ち
  ［セッションを開く］
```

### 7.3 状態の扱い

- Session の終了を Spec の完了とみなさない
- Session の最終メッセージだけから検証成功を確定しない
- 更新がない時間だけで、入力待ちや停止と推測しない
- 再開を提供するのは、実際に再開可能なセッションのみ
- 同一 Spec の複数セッションを1件に上書きしない
- Spec や Run との関連が不明な記録を、名前や時刻だけで断定して関連付けない

## 8. 検証と完了の状態モデル

画面全体で共通の判定を使用する。左サイドバーと Overview に別々の完了判定を実装しない。

| 状態 | 条件 |
|---|---|
| 実装中 | 必要な実装タスクが残っている |
| 検証条件未定義 | 実装は完了したが、必要な検証条件が決まっていない |
| 検証待ち | 必要な検証が未実施、結果未確認、または再検証が必要 |
| 検証中 | 対象に対する有効な検証実行がある |
| 検証失敗 | 現在の対象に対する必要な検証に失敗・未解決事項がある |
| 完了 | 必要な実装・検証が完了し、現在の成果物に対する成功と完了条件を確認できる |

### 8.1 検証記録

既存の検証成果物や状態モデルを調査し、少なくとも次を追跡できるようにする。

- 対象 Spec
- 検証項目・実施内容
- 成功・失敗・未実施・結果不明
- 実施時刻
- 対象成果物の識別情報
- 結果の根拠となるログ・レポート
- 関連する Run / Session。存在する場合のみ

成果物の識別方法は既存実装に合わせて設計する。コミットされていない変更も検出対象に含め、コミットIDだけで現在の内容との一致を判定しない。

### 8.2 変更後の再検証

実装・要件・設計・検証条件など、検証の有効性に関わる変更が発生した場合、以前の成功結果をそのまま現在の完了根拠に使わない。

変更対象と検証の対応を判定できる場合は、影響する検証を再実施する。判定できない場合は結果を保持したうえで「現在の状態への適用は未確認」とし、再検証へ誘導する。

過去の成功記録は削除しない。

### 8.3 既存データとの互換性

既存の done が実装タスクの完了だけを表す場合、検証済みへ自動変換しない。

実装完了の事実は保持し、検証記録が不足するものは「検証待ち・既存の検証結果未確認」として扱う。既存成果物から有効な検証結果を確認できる場合は、それを利用する。

既存の仕様ファイルのスキーマや外部ツールとの互換性を確認し、拡張独自の状態を保存する必要があれば保存先・移行方法を明示する。

## 9. ビュー間の連動

```text
Specs で対象を選択
  → Tasks が対象 Spec に切り替わる
  → Sessions が対象 Spec に絞られる

Tasks から実装を開始
  → 実行中タスクと Run / Session を関連表示

実装タスクが完了
  → Specs は検証待ち
  → Tasks は検証の残作業を表示
  → 次の操作は検証開始

検証が成功し、完了条件を満たす
  → Specs と Overview が同じ判定で完了表示

検証が失敗
  → 結果と修正対象への導線を表示
  → 修正後に再検証
```

Spec 切り替え時に実行は中断しない。Spec ごとの選択・展開状態・閲覧位置を可能な範囲で保持する。

## 10. 実装順序

1. 既存の状態・検証記録・実行機構を確認し、共通の完了判定を定義する
2. Specs に検証工程を追加し、実装完了と Spec 完了を分離する
3. Tasks に実装進捗と検証状態を分けて表示する
4. Specs の選択と Tasks / Sessions の表示を連動させる
5. 次の操作、重複実行防止、再開導線を整理する
6. 変更後の再検証判定と既存データの扱いを整える
7. Overview と判定・表示の整合性を確認する

## 11. 受け入れ条件

- 実装タスクがすべて完了しても、未検証なら Spec は完了にならない
- Specs に検証工程が表示され、実装後の次の操作が分かる
- 検証条件未定義・未実施・失敗・成功を区別できる
- 必要な検証の一部だけの成功では完了にならない
- 検証 Run / Session の正常終了だけでは完了にならない
- 有効な検証結果が現在の成果物に対応し、完了条件を満たす場合に完了になる
- 検証に影響する変更後は再検証が必要な状態になる
- 既存の done を根拠なく検証済みへ移行しない
- Tasks と Sessions に対象 Spec が明示される
- 実行中の対象、入力待ち、終了履歴を区別できる
- Spec 切り替えや画面更新で実行・選択・閲覧位置が不用意に失われない
- Overview と左サイドバーで同じ Spec の完了状態が一致する
